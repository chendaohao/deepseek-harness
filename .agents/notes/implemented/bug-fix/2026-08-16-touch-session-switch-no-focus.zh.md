# Agent Note: 触屏优先的 Web 设备在切换会话时不重新聚焦输入框

Status: implemented

[English](2026-08-16-touch-session-switch-no-focus.md) | 中文

## 问题

输入栏的解锁 effect 会在挂载时以及每次切换会话时重新聚焦文本域。对精细指针设备来说，这种聚焦是为了键盘连续性：切换会话后用户可以立即打字，而光标定位也能让长草稿停在末尾。但在触屏优先的设备上，同样的无手势聚焦会弹出虚拟键盘——手机用户只是在列表里点了一下会话，半个屏幕就被键盘盖住；初次加载页面时键盘同样会弹出。

## 决策

`packages/client/ui-conversation/src/client/skeleton/InputBar.tsx` 中的解锁 effect 在主要输入方式不具备悬停能力时跳过 `focus()`——即 `window.matchMedia('(hover: none)').matches`，每个输入栏通过 ref 只求值一次，与 `Tooltip` 已用于粗指针输入的探测一致。草稿滚动区内的光标定位仍然执行：它只移动输入框自身的滚动区，从不动对话记录，因此恢复出的长草稿依然停在光标处。精细指针设备的行为不变，包括没有 `matchMedia` 的浏览器（jsdom），此时探测结果按精细指针处理。

## 考虑过的替代方案

**改用 `(pointer: coarse)` 而不是 `(hover: none)` 来跳过。** `pointer: coarse` 会命中主指针是触控板或鼠标的可触屏笔记本电脑；这些用户理应保留键盘连续性，而且在那些设备上聚焦并不会强制弹出虚拟键盘。`hover: none` 恰好针对「无手势聚焦会弹出键盘」的设备，也是本代码库为粗指针输入类 UI 决策统一采用的探测。

**只在切换由指针发起时跳过聚焦。** 「最近发生过 pointerdown」的检查可以保住混合设备上由键盘驱动的会话切换的重聚焦，但它引入了第二种有状态的机制，而且挂载场景（页面加载）仍然需要媒体查询探测——用两套机制覆盖同一行为，而目标设备类别（`hover: none` 且外接实体键盘）本来就由平台自身抑制软键盘。

**先聚焦，再立即失焦。** 聚焦后失焦在移动端仍会闪现一帧键盘，而且对辅助技术的聚焦语义含糊不清；完全不聚焦更简单，对用户而言可观察到的结果也相同。

## 后果

- 手机用户切换会话时不再弹出键盘；点击输入框会以原生方式聚焦，与手势的直觉完全一致。
- 桌面端的键盘连续性不变：切换会话后焦点仍以 `preventScroll` 方式回到输入栏，长草稿的光标也仍会被定位。
- 处于无悬停状态的混合设备（未连接触控板或键盘的平板）同样跳过重聚焦；接上外设后 `hover: none` 不再匹配，连续性随之恢复，与平台实际抑制软键盘的时机一致。
- 该行为由 `input-bar.client.spec.tsx`（「a session switch on a touch-primary device reveals the caret without taking focus」）钉住：桩化的 `matchMedia` 报告 `matches: true`，切换会话的重渲染执行了光标定位，而文本域没有收到焦点。
