# Agent Note: 已发布迁移边接纳该时代的 payload 版本，且单条被拒日志不再拖垮搜索

Status: implemented

[English](2026-09-17-released-descriptor-version-window.md) | 中文

## 问题

v0→v1 边直接拒绝了 descriptor 版本 2，而这次拒绝把全文检索一并拖垮了。携带 `version: 2` 的 `subagent/descriptor` 事件抛出 `subagent/descriptor 0 uses unsupported descriptor version 2`；session-search 索引器把任何无法读取的冷日志视为一次失败的 observation，于是**一条**这样的日志让**每一次**搜索都失败——不只是本该命中它的那些查询。用户可见的症状是：侧边栏搜索对任何关键词都返回错误。

这次故障由两个彼此独立的缺陷共同造成，各自按其自身性质修复：清单拒绝了一个该时代写入端确实产出过的版本；而索引器允许单条不可读来源剥夺其余全部会话的查询资格。只修第一项，第二项仍会被另外 4 条无关日志触发。

该检查假设 v0 时代的写入端只产出过 descriptor 版本 3。记录与这个假设相悖。`SUBAGENT_DESCRIPTOR_VERSION` 在 2026-07-23、07-27、08-24 三次变动（1 → 2 → 3），而 `SESSION_FORMAT_VERSION` 直到 2026-08-31 才离开 0——也就是说 v0 时代横跨了全部三个 descriptor 版本。最早的产品 tag `dsh-v0.1.0-rc.7` 就已经是「格式 v0 + descriptor 版本 2」，全部 17 个发布 tag 携带的版本只有 2 和 3。版本 1 早于首个 tag，从未发布。

缺口很窄：descriptor 版本 2 与版本 3 只差一个可选成员 `agentReasoningEffort`，那是版本 3 新增的。其余成员完全一致，因此版本 3 的读取端能完整解读版本 2 的 payload。`foldSubagentDescriptor` 对无法识别的版本本来就返回 `undefined` 而非抛错，说明下游消费者早已按「容忍读不出的 descriptor」设计。

## 决策

v0 清单接纳已发布写入端可能产出过的 descriptor 版本，并把它们登记在该时代其余词汇所在的位置：

1. `RELEASED_SUBAGENT_DESCRIPTOR_VERSIONS = [2, 3]` 进入 `dispositions.ts`。两处校验点——`validation.ts` 的源级守卫与 `payload-validation.ts` 的 payload 级 `literalValue`——读取同一个常量，因此不会各自漂移。
2. 该列表硬编码，而不是读取 `SUBAGENT_DESCRIPTOR_VERSION`。已发布的迁移边冻结的是**它自己时代**的写入端产出过的词汇；从安装态包派生，会让后续构建放行 v0 写入端不可能产出的版本。
3. 版本 1 继续拒绝。它从未发布，且缺少本清单要求的 `mode` 成员——接纳它等于凭空猜测字节里并不存在的生命周期模式。

这与[清单增长规则](2026-09-06-released-format-inventory-event-growth.zh.md)属于同一缺陷类别，修法也相同：拒绝策略本身是对的，缺的是清单记录。那条 note 为 v0 清单补的是一个事件**类型**；本条补的是一个嵌套 payload 的**可接纳版本**。`subagent/descriptor` 的 `version` 成员与事件类型一样，属于时代冻结词汇。

### 单条被拒日志不得剥夺其余全部会话

放宽清单修好了 11 条日志，却没有恢复服务——因为索引器的失败从来不是 descriptor 版本特有的。另有 4 条日志被既定策略永久拒绝：3 条携带 `vision/observed` 事件，该事件来自只存在于某条开发分支的插件；1 条是被 v2→v3 时序规则拒绝的 Claude 导入。其中任何一条都能单独让全部搜索失败。

session-search 的 observer 现在会跳过被其格式迁移边永久拒绝的存量日志，并按会话 id 告警一次。`SessionFormatUnsupportedError` 是唯一被跳过的类别。它标记的是**单条来源**的既定属性——重试无法索引它，其他任何会话也不依赖它——所以这里的选择是「一条日志不可搜」还是「搜索整体不可用」，而不是「成功」与「失败」。后端失败与损坏仍然使 observation 失败，因为它们可能在重试后消失，或描述的是存储而非单条来源。

被跳过的会话内容保持不可搜，直到能读取它的构建为其建立索引。这是排除策略的诚实边界：它把「无法回答的查询」换成「缺失的结果」而非报错，并且告警点名了缺失的是哪个会话，使这一缺口可被发现。

## 后果

- 携带 descriptor 版本 2 的已发布 v0 日志恢复可读。在报告该问题的机器上，11 条存量会话重新可读。
- v1→v2 与 v2→v3 边调用同一个 `assertReleasedPayloadSemantics`，因此继承了放宽后的窗口。这是正确的结果而非副作用：这些边在通往当前世代的路上校验同一批历史 payload，而版本 2 的 descriptor 在再往后一条边上并不会变得更难解读。原生 V3 校验不受影响——`assertV3Event` 只校验信封，不调用该 payload 校验器。
- 版本 3 仍是当前写入端唯一产出的版本。在冻结边里接纳版本 2，并不放宽新增追加可以携带的内容；那由 `SUBAGENT_DESCRIPTOR_VERSION` 继续管辖。
- 该机器上的全文检索恢复可用：252 条存量日志中 215 条进入索引，4 条被拒日志以告警方式排除，而不再让每次查询失败。
- 读不了某条存量日志的部署，现在得到的是**部分**搜索而非完全没有。这正是预期的取舍：此前的行为把「一条会话不可读」静默转换成「整个功能不可用」，这也是本次事故难以诊断的原因——报错指出的是 descriptor 版本，而症状是侧边栏一片空白。

## 已考虑的替代方案

- **只让索引器跳过不可读日志**：否决。单靠它会掩盖清单缺口：11 条日志是合法历史，正确的构建必须能读，跳过等于把其内容永久静默丢弃。跳过只对**既定且永久**的拒绝成立，因此它只识别一个错误类别，而不是任何读取失败。
- **任一来源被拒就让整次 observation 失败**：本 note 之前的已发布行为，予以否决。它让一条不可读日志剥夺其余全部会话的查询资格，使单个不可读文件的爆炸半径等于整个功能。
- **连 descriptor 版本 1 一起接纳**：否决。没有任何发布 tag 携带过它，且其 payload 缺少本清单要求的 `mode` 成员，因此无法从这些字节中合理地判定子代理是一次性还是可续接。
- **从 `SUBAGENT_DESCRIPTOR_VERSION` 读取版本窗口**：按「决策」中的理由否决：它把冻结边耦合到移动的包上，并会放行 v0 写入端不可能产出的未来版本。
- **特判为「接受一切低于当前版本的值」**：否决。该窗口是关于已发布写入端的**记录事实**，不是「越新越好」的启发式；版本 1 仍必须拒绝。
- **把 `vision/observed` 加进 v0 清单**：否决。该事件在本检出中不是第一方事件——此处没有任何构建解读它——接纳它等于把一个无法解读的事件带进已提交世代，而这正是封闭清单规则所拒绝的。（在确实定义过它的那条开发分支上，该清单记录是另一个仍然存在的缺口。）

## 测试

- `session-format-v0-to-v1/tests/validation.spec.ts` 恢复携带 descriptor 版本 2 与 3 的真实 v0 行，并断言版本 1 与 4 仍抛出 `SessionFormatUnsupportedMigrationError` 且点名该版本号。把常量改回 `[3]` 会让该测试以生产环境一模一样的错误失败。
- 有效样例清单新增两种生命周期模式的版本 2 descriptor payload，其中一条包含版本 3 后来才加入的可选成员。
- `session-query-sqlite/tests/sqlite.spec.ts` 在一条可读会话旁存放一条被冻结清单拒绝的已发布 v0 日志，断言可读会话保持可搜、被拒会话不产生索引行、且恰有一条告警点名它。移除跳过逻辑会让该测试以生产环境的 `persistence observation failed` 错误失败。
- 把最初报错的存量日志通过真实格式 catalog 与相邻迁移链恢复，得到 v3 artifact，且版本 2 的 descriptor 原样保留。
