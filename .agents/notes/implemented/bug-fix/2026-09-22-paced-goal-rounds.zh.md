# Agent Note: 为无人值守的 goal Round 定速

Status: implemented

[English](2026-09-22-paced-goal-rounds.md) | 中文

## 问题

驱动器在每个 idle 点都预留一轮。goal 处于 armed 状态时，一个 turn 结束后立刻排入下一轮，因此等待后台工作的无人值守 goal，会以自身 turn 完成的速度重新进入模型，而不是以其处境变化的速度。

一次实测的编排会话让代价变得具体：7 分钟内 16 轮、160 万 token、约占该会话指挥侧开销的 11%，且其中没有任何一轮有进展。每个 Round 都是在上下文已接近 30 万 token 之上的一次完整请求，因此这个循环随空闲时间而不是随工作量增长。它最终停止，只是因为有人在 UI 上暂停了 goal，而运维方的 preset 还必须携带一段文字，告诉模型在 Round 不再有进展时自行暂停 goal——模型是在 16 轮之后才照做的，而不是之前。

Round 是驱动器拥有的唯一自主唤醒手段，因此不加节流的它同时也决定了一个等待中的 goal 花钱的频率。

## 决策

[`@deepseek-ai/dsh-goal-round-driver`](../../../../packages/goal/goal-round-driver/) 新增 `roundIntervalMs` 配置字段，单位为毫秒，默认 `1800000`（30 分钟）。它是驱动器唯一的设置；`maxGoalRounds` 留在 goal 定义里，阻塞阈值留在 `dsh-tool-goal` 里，因为那些是驱动器不得重复拥有的策略。

该间隔是预留之间的最小间距，而不是 idle 计时器。闸门位于 `drive()` 中紧挨预留之前，因此没有任何触发路径能绕过它——包括定时器本身在内的每一个 `requestDrive` 调用方，都会重新进入同一处检查。落在间隔内的 idle 点会为剩余时间设置一个定时器并返回；该定时器被 `unref`，因此待处理的 Round 绝不会拖住宿主进程。

有两种情况跳过等待。`roundsStarted` 仍为 0 的 goal 没有上一次预留，因此它的第一轮在下一个 idle 点启动。显式的 `goal/changed`——create、edit、resume——会清除记录的预留时间，因为生命周期变更是新的授权，而不是无人值守的漂移。

teardown 与 agent 销毁会取消待处理的定时器，因此已卸载的驱动器无法唤醒它不再拥有的生命周期。预留时间戳是进程内的调度状态：它不持久，重新加载后会在不记得上一间隔的情况下继续。

本决策取代 [Same-session goal-round driver](../../archived/feature/2026-07-19-same-session-goal-round-driver.md) 的「插件没有配置」约定；该笔记关于预留、栅栏、检查点与 teardown 的决策保持不变。

## 曾考虑的替代方案

**检测无进展的 Round 并退避。** 驱动器需要一个「进展」的定义，而它在此处能观察到的一切候选——工具调用、输出长度、工作区差异——都是模型可以在毫无进展的情况下满足的代理指标。实测会话里的 Round 确实调用了工具；它们把同一条 `git status` 跑了五遍。

**在 `create_goal` 上加 per-goal 的 `round_interval_ms`。** 这是让一个 goal 拥有与另一个不同节奏的唯一办法，被否决是因为波及面：goal 记录是持久的，该字段会进入会话格式、fold schema、工具 schema、两个 SDK 的期望输出以及每一个 goal 快照，而且模型必须在每次 create 时记得传入。一个 host 设置足以覆盖已观察到的需求——无人值守编排是实践中唯一的 goal 用法。

**保留立即重排，让模型自行暂停 goal。** 这是已发布的行为，preset 也带着那条指令。它依赖模型识别出一种它没有廉价办法度量的空转，并且在模型做出判断之前就把 token 花掉了。

**让第一轮也等满间隔。** 更统一也更简单，但创建 goal 后将 30 分钟毫无动静。预留才是自然的边界：第一个预留没有可以与之定速的前驱。

**用指数退避代替固定间隔。** 早期响应快、后期便宜，但它让唤醒时刻成为 Round 数量的函数而不是已流逝时间的函数，运维者无法预测下一轮何时到来。

## 后果

无人值守的 goal 每个间隔花一次模型请求，而不是每个 idle 点一次。在实测会话中，那段病态窗口——7 分钟 16 轮——塌缩为一轮，结束该循环的人工干预也不再需要。30 分钟的默认值改变了每一个既有 goal 用户的行为，而不只是报告成本的那套部署；`roundIntervalMs: 0` 恢复此前的行为，而断言精确 Round 序列的场景现在会显式设置它。

代价是驱动器无法缩短的延迟。下一步不依赖任何外部事物的 goal，现在每个间隔推进一轮，而此前它能以模型的最快速度推进。worker 与 subagent 的结算仍会立即唤醒会话，因此等待委派工作的 goal 保持了响应性；等待模型自己想出下一步的 goal 则不然。

该间隔基于墙上时钟，因此时钟前跳可能缩短一次间隔，后跳可能拉长一次。对于一个定速下限而言两者都无害，也都不值得引入调度面上其他地方并不使用的单调时钟。

被拒绝的预留现在同样消耗间隔。这是刻意的——正是它让限速无法被绕过——也意味着在间隔中途被编辑的 goal，只有在间隔之后才会在新修订上继续，除非该编辑本身重新授权了一轮立即执行。
