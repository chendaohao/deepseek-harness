# Agent Note: API extractor 报告

Status: proposed

[English](2026-06-11-api-extractor-reports.md) | 中文

> 文档块类型检查与事件分类体系两部分已交付（[doc-sync（文档同步门禁）强制](../../archived/process/2026-06-11-doc-sync-enforcement.md)）；剩余的 API 报告部分作为独立提案被推迟，直到下列条件使其值得实施。

## 问题

公开 API 的变更是不可见的：没有任何机制将「此次提交改变了公开接口」变为一个显式、可评审的事实。评审者阅读 diff 时可能遗漏某个导出类型新增了字段，或某个方法签名发生了变化。

[发布族](../../../../scripts/release/families.ts)把每个非 private 的 `packages/*/*` 与 `apps/*` 清单以同一个共享版本发布到 npm。因此外部消费方可以依赖 `@deepseek-ai/dsh-*` 的各个入口，而一次无意的字段放宽或签名变化会以版本变更的形式抵达他们，而不是在评审中被发现。

## 提案

使用 api-extractor（或 `tsc --emitDeclarationOnly` 加一份规范化的公开 API 清单）为每个已发布包生成一份签入仓库的 `etc/<pkg>.api.md`；CI 在重新生成结果与已签入报告不一致时失败。这样，每一次公开 API 变更都会成为评审者（或评审 agent（智能体））必须看到的一行 diff。

范围以发布族的已发布集合为准，而不是每一份工作区清单：标记为 `private` 的包不发布任何内容，因此不携带报告。

## 曾考虑的替代方案

**`tsc --emitDeclarationOnly` 加规范化的公开 API 清单**：如果 api-extractor 过于笨重，这是更轻量的机制；两者都能满足提案所需的「签入仓库、可 diff」的报告形态。

**扩展类型等价清单。** [`verify-type-equiv`](../../../../scripts/verify-type-equiv.ts) 已经把具名声明钉在源码 JSDoc 上，但它只覆盖文档选择引用的符号。本提案补的是完整性而非准确性：每个入口的报告会列出全部导出，包括没有任何页面引用的那些。

**把 private 包也纳入。** `private: true` 的清单不发布任何内容，也没有外部消费方，为它生成 `etc/<pkg>.api.md` 只会增加重新生成成本与 diff 噪音，而没有读者。

## 验收标准

- 每个已发布包都有一份签入仓库的 `etc/<pkg>.api.md`；CI 在重新生成结果与已提交报告不一致时失败。
- 公开 API 变更（新增导出、字段放宽、签名变化）在评审中以报告 diff 行的形式可见。
- private 包不携带报告，且范围检查从发布族推导已发布集合，而不是维护一份手工清单。

## 风险

该依赖笨重且难以调教，且报告格式会随编译器升级而变动。包数量会放大重新生成成本：本族覆盖约 350 个可发布包，因此逐包报告是昂贵的形态，而逐入口报告在执行前需要先测量。

[API 预稳定策略](../../../../AGENTS.md)允许任何公开 API 要求所有消费方同步改动，且不提供兼容承诺，因此报告记录的是破坏，而非阻止破坏。本提案的价值仅在于评审可见性。

## 重新评估条件

当初的推迟建立在一个前提上：「各包尚未发布」。该前提已不成立。[发布族](../../../../scripts/release/families.ts) 把 `@deepseek-ai/dsh-*` 发布到 npm，因此本提案要使其可见的那层接口，正是外部消费方实际安装的接口。

当初判断正确的部分是成本，而非价值。对约 350 个可发布包做报告生成是昂贵的，且目前没有任何测量能证明这种变动成本可以承受。因此实施从测量开始，而不是从采纳开始：

- 在已发布集合上测量重新生成耗时与报告 diff 大小。
- 若逐包报告过于昂贵，则采用上文 `tsc --emitDeclarationOnly` 的形态，或把报告收窄到已发布插件实际导入的包。

在取得该测量之前，提案保持 proposed。仅凭「已发布」不足以证明这些报告值回其维护成本；它移除的是「没有外部接口需要保护」这一论据。
